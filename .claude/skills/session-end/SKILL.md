## 冒頭に置く前提

このリポジトリでは **向きは「誰が書くか」で決まる**。

★ **「Notion が正本」とだけ覚えないこと。** 2026-08-01 にこの言い方は不正確と訂正されている（下の CURRENT_SPEC の節を参照）。

| 誰が書くか | 正本 | 例 |
|---|---|---|
| 人・チャットが決めて書く | **Notion** | DECISION_LOG／コアコンセプト／タスクページ／運用文書 |
| Claude Code が生成する | **repo** | SESSION_STATE／CURRENT_SPEC |
| 実装から導出できる事実 | **コード** | 依頼一覧／解放ツリー／各種の表 |

ローカルへの追記が暫定記録になるのは **Notion が正本の文書だけ**。repo が正本のものは、**ローカルが正で Notion が生成物**。

このスキルは、正本と写し・生成物の反映を両方向とも漏れなく行うためのもの。

### ★ SESSION_STATE の向きは企画ごとに違う（2026-07-29 改訂）

**このスキルは複数のリポジトリへ配られる。SESSION_STATE がどちら向きかは企画ごとに違うので、決め打ちしないこと。**

| 企画 | SESSION_STATE の正本 |
|---|---|
| 遠征ギルドログ | **repo**（`docs/SESSION_STATE.md`）。Notion は閲覧用の写し |
| 天使様（IGPJ_02） | **Notion**。`docs/SESSION_STATE.md` は写し |

★ **向きは必ず `CLAUDE.md` と、各文書の冒頭の宣言を見て判断する。**

**repo が正本の場合の理由**：SESSION_STATE は **Claude Code が生成して Claude Code が読む**。Notion を正本にすると、生成したものを人が手で運ぶ工程が発生し、運び忘れた瞬間に**古い現在地を配る文書**になる。Notion 側の写しはスマホから見るための閲覧用で、人が手で編集してはいけない。

⚠️⚠️ **Notion が正本の場合は、⑤-b の全置換を行ってはいけない。**

- その企画では**チャット側（設計担当の Claude）も同じページを直接書き換えている**。全置換すると**チャット側の記述を消す**
- この場合は **`update_content` で、自分が持つ節（実装状況・次にやることの実装分・判断待ち）だけを外科的に更新**する
- 向きが分からなければ**停止して尋ねる**

## ④-b PR をマージして main を追いつかせる（2026-09-11 追加）

リモート実行のセッションでは push 先が作成時に固定され、main へ直接押せない。

- **push 後に PR をマージし、main が現 HEAD を含むことを確認する**
- ★ **理由：コンテナは main からクローンして起動する。** main が古いままだと、毎回古い状態で起動して①の早送りに頼ることになる（2026-08 に、約4週間古いクローンで起動して生成物が欠けかけた事故あり）
- ★ **手順ではなく状態で直す**。早送りは安全網であって、毎回の前提にしない

### ★ 配信は作業の完了時にその場で行う（2026-09-22 追加）

- ★ **実装が完了したら、その場で PR をマージして配信する。session-end を待たない**
- ★ **session-end は記録の反映に専念する**。④-b は、作業中に配信し損ねたものを拾う位置づけ
- 理由：★ **作者は実機（GitHub Pages）で確かめる。** マージを後回しにすると、実装済みの機能が実機に出ない。2026-09-21 に EX-140・141 のマージを session-end に回したため、作者が「記録を綴じる」ボタンを実機で見つけられなかった（EX-139 までは完了ごとにマージしていた）

## ② DECISION_LOG.md 更新

既存フォーマットに合わせて追記する。**追記位置（冒頭か末尾か）はファイル側の規約に従う。** ファイルに明記がなければ既存エントリの並び順から判断する。日付は実際の日付を確認して使う。

項目：`## YYYY-MM-DD: <決定を1行で>` の見出しの下に、**決定** ／ **理由** ／ **却下した案** ／ **根拠・参考** の4つ。

★ **見出しの形はこの形に限る**（2026-10-09 訂正）。却下案索引はこの形しか拾わない。以前ここに「# 日付｜決定」と書いてあり、そのとおりに書くと索引に1件も拾われなかった（EX-118）

★ **「却下した案」を空欄にしないこと。**

却下案と理由を残すのがこのログの主目的。将来のAIが同じ案を再提案するのを防ぐため。却下案が本当に無かった場合のみ「なし（対立案が出なかった）」と明記する。

★ **チャット側が直接書いた節は、却下欄が無い形式のまま取り込む**（2026-09-14 追加）。判断基準の記録など、**却下を伴わない裁定**があるため。欄が空なのは欠落ではなく性質で、索引の「項が無いエントリ」が増えるのは正しい反映。取り込むときは**書き手を明記**する

# 停止条件

以下に当たったら、作業を止めてユーザーに判断を仰ぐ。勝手に決めて記録すると、誤った内容が正本に入る。

1. 今回の決定が Notion の既存記述と矛盾する
2. 今回の決定が DECISION_LOG で既に却下済みの案に該当する
3. 設計判断かどうかの分類がつかない
4. Notion のどのページに書くべきか判断がつかない
5. コミット対象に意図しないファイルが含まれている
6. **検証の修正を 2 回試しても通らない**
7. **CURRENT_SPEC のローカルと Notion の片側しか当たらない**（3-b と 5-c はセット。片方だけ成功した状態で進めない）

## ★★ 止まる前に：戻せるかを判定する（2026-09-25 採用）

実装中に判断が要る場面に来たら、止まる前に**その判断が後から戻せるか**を判定する。

- **戻せる**（値・文面・可逆なルール）→ 「問い」を書いて、**既定の行動で先へ進む**。止まらない
- **戻せない**（データ構造・セーブ形式・基準の意味）→ 停止。下の7項目の形式で
- **矛盾・却下済みに当たる**（停止条件1・2）→ 停止

問いの形式（SESSION_STATE の「判断待ち」節に表で書く）：

| ID | 緊急度 | 問い | 既定の行動 | 戻せる根拠 |
|---|---|---|---|---|

- **既定の行動**：答えが来なければこうする、を1行で。これで実装する
- **戻せる根拠**：なぜ後から覆せるか（例：定数1つ／文面のみ／対比較で差が出ない）。★ **書けないなら、それは戻せない判断なので停止する**。分類を善意に任せず、書けるかどうかで振り分けるための欄
- **緊急度**：同じ領域の次の作業の前に裁定が要るか

規則：

- ★ **既定の行動で進んだ問いは、同じ領域の次の作業の前に裁定する**。未裁定の問いが残っている領域には、自走は入らず止まる（溜めないため）
- ★ **これは「ユーザーに確認せずに新しい仕様を決める」ではない**。問いを書いて申告し、既定の行動は仮置き。裁定されるまで確定ではない。裁定で覆ったら戻す
- 完了時の5項目の4（はみ出した点・未対応）に、既定の行動で進んだ問いの件数を書く

理由：EX-144（2026-09-23）で Code は、止まるべき設計判断4件を止まらず仮置きして申告した。申告されていたので後から裁定でき、自走は回った。「値か設計判断か」の境目が曖昧だったのを、「戻せるか」に軸を変えて規則化した。表の形は X 投稿（@AM09:21、2026-09-24）の自律開発ダッシュボードの「既定の行動」列から。「戻せる根拠」の列はチャット側の追加。詳細は 02_operations/自走の手順

## 停止時に出力する形式（2026-07-29 改訂：4項目→7項目）

「止まりました」だけでは判断できない。必ず次の**7項目**を出す。

★ 順序と項目数は **02_operations/ドキュメント運用規約「貼り付けブロック」節**に合わせること。欄の名前や区切りの整形は変えてよいが、**数と順序は変えない**。

1. **見出し**：要裁定とタスク名
2. **ページIDと、書いた節の名前**
3. **論点**（1行）
4. **A の内容**（1行。推奨があればその旨）
5. **B の内容**（1行）
6. **トレードオフ**（A と B をそれぞれ一言）
7. **既に却下済みの案があればそれ。なければ「なし」**

★★ **規則（ここが要）**

- このブロックは**要約であって正本ではない**。正本はタスクページ
- **ブロックだけ読んで裁定できる粒度にする。「詳細はページ参照」で済ませない。** それをやるとチャット側がページを全文取得することになり、トークン消費が大きい。**節約のための仕組みなので、粒度を落とすと目的が消える**
- 最後は **A/B の一問一答で答えられる形**まで畳む（ユーザーは移動中に音声で返答することがある）
- ★ **ただし「C：前提が違う／どちらも違う」を常に有効な回答として末尾に明記する**（2026-09-09追加）。選択肢を2つに畳むと、畳んだ側が枠を決め、答える側はその外が見えなくなる。C が返ってきたら理由を問わず、論点の立て方からやり直す。「なんか違う」だけで成立する回答。末尾の行は「→ A / B / C（前提が違う）」の形にする

```
【論点】<何を決める必要があるか・1行>

【選択肢】
A: <案>
B: <案>

【トレードオフ】
A: 得られるもの / 失うもの
B: 得られるもの / 失うもの

【却下済みか】
DECISION_LOG を確認した結果：<既出の有無。既出ならその日付と理由>

→ A / B どちらにしますか
```

★ 最後は **A/B の一問一答で答えられる形**まで畳むこと。（上のコードブロックは**旧4項目版の雛形**。**2026-07-29 以降は上記7項目を使うこと**）

## ★★ 停止報告は、出す前にセルフレビューをかける（2026-09-12 正式運用）

要裁定ブロックを出す前に、**Task ツールでサブエージェントを1つ立て、そのブロックを叩かせてから出す**。

渡す観点5つ：

1. ★ この論点は本当にA/Bの二択か。二択に畳んだことで、より良い第三の選択肢が見えなくなっていないか
2. 前提そのものが間違っていないか（Xすべきかと問う前に、そもそもXが必要かを疑う）
3. 裁定者がこのブロックだけを読んで判断できるか。欠けている情報は何か
4. A/B の記述は公平か。どちらかに誘導していないか
5. 却下済みの案を再提案していないか

規則：

- ★ **指摘を鵜呑みにしない。効くものは自分で再実測して裏を取る**（レビュー側が誤っていた例も実際にある）
- レビューで何を指摘され、どう直したか（または直さなかった理由）を、**停止報告の末尾に2〜3行で添える**
- ★ **急いでいても省かない。** 5回の試行で毎回3〜6件の誤りを出す前に検出し、**論点そのものの取り違え**も捕まえた
- 戻し条件：指摘が形式的になり、実害のある誤りを拾わなくなったとき

# CURRENT_SPEC の扱い（2026-08-01 追加）

## ★裁定：ローカルが唯一の書き場所。Notion は生成物（全置換が原則、2026-08-06 から 3条件で差分更新も可）

`docs/CURRENT_SPEC.md` を**唯一の書き場所**とし、session-end が **Notion 側を生成物として更新する**（全置換が原則。下の「手順に足すこと」の 3条件を満たせば差分更新）。

### なぜこの向きか

CURRENT_SPEC は**実装を見て Claude Code が書き、チャット側と作者が読む**文書。

- 判断は DECISION_LOG に残る
- 思想はコアコンセプトに残る
- **CURRENT_SPEC が持っているのは「今どうなっているか」**

★ 2026-07-27 の分類（**生成する主体と読む主体が同じなら repo が正本**）がそのまま当てはまる。SESSION_STATE と同じ。

### なぜ「文言を一致させる」ではないか

**バイト単位の一致は構造的に不可能。**

1. 見出しの階層が1つずれる（Notion はページ名が H1 を占める）
2. 表の記法が違う（Notion 独自タグ 対 Markdown の縦棒）
3. バッククォート内の日本語とコードブロックが Notion で壊れる

★ **「一致させる」は実質「片方を生成物にする」という意味にしかならない。** それなら明示的にそうする。

### Notion 側のページに必ず書くこと

**生成物の宣言を先頭に置く。**

1. 生成日時
2. **これは生成物であって正本ではない。正は docs/CURRENT_SPEC.md**
3. **ここを編集しても次の更新で消える**

※ 依頼一覧の生成物に付けるのと同じ2行＋1行。**スキル側で自動出力する。人が付け忘れる余地を残さない。**

## 手順に足すこと

session-end の中で、**ローカルと Notion をセットで更新する。**

- 3-b：`docs/CURRENT_SPEC.md` を更新する
- 5-c：Notion の CURRENT_SPEC を**全置換**する
- ★ **（2026-08-06 改訂）次の3条件をすべて満たす場合に限り、全置換でなく差分の外科的更新でよい。** ①直前の全置換が同一の生成元から行われている　②前回反映時点からの差分箇所が特定できている　③書き込み後に読み直して検証し、更新箇所を報告に明記する。満たさない場合（生成元が変わった・差分が特定できない・前回反映からの経過が大きい等）は従来どおり全置換する。理由：全置換は出力を3分割して当てる必要があり、表ブロックの分割位置を誤ると壊れる。規約の目的は反映漏れの防止であり、読み直し検証を必須にすれば差分更新でも目的を満たす（詳細は遠征の DECISION_LOG 2026-08-06）
- ★ **片側しか当たらなければ停止する**

棚卸しの分類に「**仕様が変わった**」を加える。仕様が変わったのに CURRENT_SPEC を触っていなければ、そこで気づける。

### なぜ手順に入れるか

★ 2026-07-27 に **「人の手が挟むと必ずずれる。同じ操作で両方が更新される形にする」** と決め、SESSION_STATE ではそうした。**CURRENT_SPEC では同じことをしていなかった。**

その結果、2026-08-01 に**正本（Notion）が写し（ローカル）より古い**状態が発見された。07-31 の内容が丸ごと入っていなかった。

→ **同じ理由づけを、同じ性質の文書に適用していなかったのが原因。**

## 「Notion が正本」との関係

運用規約の原則は変わらない。**向きは「誰が書くか」で決まる**（2026-07-27）。

これで例外は2件になった：**SESSION_STATE と CURRENT_SPEC**。どちらも Claude Code が生成して Claude Code が読む文書。

★ **例外が2件出たということは、「Notion が正本」は原則の言い方として弱い。** 正しくは**「人やチャットが決めて書くものは Notion が正本。Claude Code が生成するものは repo が正本」**。
